# 高效提示词工程指南

提示词工程是精心编写指令，以引导 AI 语言模型生成预期结果的过程。虽然任何人都可以编写提示词，但并非所有人都能编写出始终如一地产出高质量结果的提示词。

## 什么才是好的提示词

一个提示词通常由以下几个部分组成：

1. **任务描述**：解释了我们希望模型做什么，包括我们希望它扮演的任何角色（role）或人设（persona）
2. **上下文（context）**：提供必要的背景信息
3. **示例**：用来展示期望的行为或格式
4. **具体任务**：要回答的特定问题或要执行的操作

### 系统提示词 vs 用户提示词

大多数模型的 API 允许我们将提示词分为：

- **系统提示词（system prompts）**：包含任务描述和角色扮演指令，决定模型在整个对话过程中的行为方式
- **用户提示词（user prompts）**：包含实际的任务或问题

## 核心提示技巧

### 技巧一：零样本学习（Zero-Shot Prompting）

零样本学习提示意味着在不提供任何示例的情况下向模型发出指令。在这种方法中，我们只需描述我们想要什么，模型就会尝试根据其训练来完成请求。

**最佳场景**：简单的任务，仅凭指令就能清楚地知道所需的输出。

**优势**：
- 使用更少的 Token，降低成本和延迟
- 提示词更容易编写和维护

**局限性**：当我们需要特定格式或行为时，零样本学习提示可能不够用。

### 技巧二：少样本学习（Few-Shot Prompting）

少样本学习提示涉及提供示例来演示我们希望模型如何响应。单样本提示使用单个示例，而少样本学习通常意味着两到五个或更多示例。

**示例数量建议**：对于大多数应用来说，三到五个示例能够达到很好的平衡。

**Token 优化技巧**：
- "比萨 -> 可食用"比"输入：比萨，输出：可食用"使用更少的 Token

### 技巧三：思维链（Chain-of-Thought）提示

思维链提示（CoT）涉及明确要求模型在给出答案之前逐步进行思考。

**最简单的实现方式**：在提示词中添加诸如"逐步思考"或"解释你的推理过程"等短语。

**优势**：
- 在各种基准测试中提升模型性能，特别是对于数学问题、逻辑难题和多步推理任务
- 有助于减少幻觉，因为模型必须用明确的推理步骤来证明其答案的合理性

**代价**：延迟和成本的增加。

### 技巧四：角色（Role）提示

角色提示为模型指定了特定的身份（persona）或专业领域。通过让模型扮演特定的角色，我们会影响其响应的视角和风格。

**使用建议**：应该具体说明该角色及其任何相关特征。与其仅仅说"扮演一名老师"，不如说"扮演一名注重努力和进步的、善于鼓励的一年级教师"。

### 技巧五：提示词链与分解

提示词链涉及将复杂的任务分解为更小的、易于管理的子任务，每个子任务都有自己的提示词。

**优点**：
- 每个提示词都更容易编写和维护
- 可以独立地监控和调试每个步骤
- 可以为不同的步骤使用不同的模型
- 在可能的情况下，可以并行执行独立的步骤

**缺点**：增加了最终用户的感知延迟。

## 编写有效提示词的最佳实践

### 1. 清晰且具体

模糊性是有效提示的敌人。我们应该消除关于我们希望模型做什么的所有不确定性。

### 2. 提供充足的上下文

上下文有助于模型生成准确、相关的响应。如果我们想让模型回答有关某个文档的问题，那么在提示词中包含该文档是必不可少的。

### 3. 指定输出格式

我们应该明确说明我们希望模型如何响应：
- 简洁的答案还是详细的解释？
- 输出应该格式化为 JSON、项目符号列表还是段落？
- 模型应该包含开场白，还是应该直奔主题？

### 4. 策略性地使用示例

示例是减少模糊性的强大工具，但它们会带来 Token 和上下文长度方面的成本。当所需的格式或行为仅凭指令不够明显时，我们应该提供示例。

### 5. 迭代与实验

提示词工程是一个迭代的过程。我们很少能在第一次尝试时就写出完美的提示词。

### 6. 提示词版本控制

我们应该对提示词进行版本控制，以便随时间追踪更改。使用一致的评估数据使我们能够客观地比较不同的提示词变体。

## 需避免的常见陷阱

### 1. 过于含糊

最常见的错误之一是假设模型在没有明确解释的情况下就能理解我们的意图。像"写一些关于气候变化的内容"这样含糊的提示词留下了太多的解释空间。

### 2. 将提示词过度复杂化

虽然清晰度和细节很重要，但我们也可能会走向另一个极端。过度复杂的提示词可能会使模型感到困惑，而不是起到帮助作用。

### 3. 忽略输出格式

未能指定输出格式可能会导致问题，特别是当模型输出被输入到其他系统中时。

### 4. 测试不充分

单次成功的输出并不意味着提示词是可靠的。我们应该使用各种输入（包括边缘情况和异常场景）来测试提示词。

## 结论

有效的提示词工程结合了清晰的沟通、示例的策略性使用以及系统化的实验。

关键原则始终保持一致：
- 在指令中做到具体且清晰
- 为模型的工作提供充足的上下文
- 指定我们需要的输出格式
- 当示例能够增加价值时使用它们，并根据结果进行迭代
